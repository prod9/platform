## 1. What this is

`platform` is rescoped as a v1.0 command-line tool for PRODIGY9's infra patterns. Its
server is removed, CUE gives way to Lua, and the Kubernetes definitions move to a new Lua
library, `infra-lua`. `platform` stays a Go program. Its commands, build frameworks,
Dagger use, `release`, `publish` and existing `platform.toml` keys are unchanged.

## 2. infra-lua

A new repo, `gh:prod9/infra-lua`, inside the `infra` project. It replaces `infra-defs`,
which is archived.

**Design rule.** A value is as close as possible to the output wanted. Helpers and
metadata live in the metatable. No wrappers. Behaviour composes as functions on values.

- A **resource** is the Kubernetes object as a table; its metatable adds `:with`.
- A **pack** is the list of resources itself; names (`pack.deploy`), published values
  (`pack.out`) and `:with` come from its metatable.
- A **mixin** is a callable from resource to resource, with its name and the kinds it
  applies to in its metatable. On a resource of another kind it is an error; on a pack it
  patches every matching resource and is an error when none match.
- **Merging** unifies and never overwrites: two different values for one field fail.
- **Inputs** are checked for unknown names, missing required names and type, and errors
  name the app file and line.

The reference for these shapes is `infra-defs/spike/nocue/fp.lua`.

**Contents.**

- The library: every kind, pack and mixin of defs v0.4.7, with its design principles and
  specs rewritten for Lua. The two open v0.4.7 defects (resource requests on a workload
  with an init container; `PriorityClass` fields) do not carry over.
- Helpers for editing upstream manifests: documents arrive as resource tables and are
  edited with ordinary Lua.
- `templates/`: copy-pastable Lua files for the cluster baseline (cert-manager, Flux,
  NGINX Gateway with the Gateway API definitions, and the gateway, issuer and Flux-sync
  apps `platform` scaffolds today, without the platform server). They are files a repo
  copies and then owns, not functions the library exposes. Each declares its vars and
  their defaults at the top: `local vars = platform.vars {CERT_MANAGER_VERSION = "v1.20.2"}`.
- A defs-to-Lua migration guide.

**Packaging.** A LuaRocks rock: a rockspec at the root, `templates` listed as a shipped
directory. Rocks are published to ghcr. The library is written for Lua 5.1, the version
the VM inside `platform` implements, and its tests run on that VM.

## 3. platform v1.0

**Recorded first.** New decision records, written before any code, each naming the
records it supersedes; no existing record is deleted or edited:

1. CUE dropped; `render` runs Lua with `infra-lua` fetched as rocks.
2. Server removed; `platform` is a CLI.
3. `.platform` DSL removed; Lua templates ship in the rock.
4. Schema validation inside `render`.

Specs are rewritten to match in the same slice, ahead of implementation.

**Removed.**

- Server: `srv/` with its migrations, `webui/`, the `srv` and `worker` commands, the
  `[server]` config, `engine/checkout.go` and `engine/inspection.go` (called only by the
  server), the scaffold template that deploys the server and its engine pool, and the Go
  dependencies nothing else needs. Tag `v0.10.0` is the last commit with the server.
- CUE: the linked engine, `cuemod/`, the CUE dependency fetch, the CUE scaffold files.
- The `.platform` DSL: `dsl/` and its render route.
- Specs, guides and vendor notes about the removed parts.

**`render`.**

- Runs each `apps/*.lua` on `gopher-lua`, a pure-Go VM implementing Lua 5.1, sandboxed:
  no file, process, clock or random access. Lua 5.4 and 5.5 VMs for Go were surveyed and
  set aside (chakrit: "stick with gopher-lua and lua 5.1"); the survey is summarised in
  the engram ledger.
- `infra-lua` is not built in. The version is pinned in `platform.toml`; `platform`
  fetches that rock from ghcr with a small built-in fetcher and unpacks it into
  `$XDG_CACHE_HOME/platform/rocks/<name>/<version>/`. A version already there is not
  fetched again.
- `[vars]` from `platform.toml` are injected as `platform.vars`.
- Output contract unchanged: component, then file name, then a list of documents; the
  infra image keeps exactly one layer.
- Validation: each document is checked against the schema for its own `apiVersion` and
  `kind`, taken from Kubernetes' published OpenAPI files and, for custom resources, from
  the schema inside the CRD definition. Schemas are fetched once into the XDG cache. The
  check uses a generic JSON Schema library, `google/jsonschema-go`; no Kubernetes
  library, no version setting. A failing document stops the render before anything is
  written.

**`init`.** As today, with the rock as the source: prompt, download the `infra-lua` rock,
write every template into `apps/`, write the templates' declared vars and defaults into
`[vars]` (keeping values already set), pin the rock version, write the launcher, confirm,
apply. No checklist.

**Publishing rocks.** Through Dagger, the same way `platform publish` pushes the infra
image.

**Also written.** A v0-to-v1 guide; the v1.0 release.

## 5. Spikes before the code they inform

1. **Validation.** `google/jsonschema-go` against Kubernetes' OpenAPI files (which use
   the OpenAPI 3.0 dialect, while the library validates draft 2020-12) and against a CRD
   schema. Also settles what `render` does with a kind it finds no schema for.
2. **Private ghcr.** Authenticated pull with the `REGISTRY*` credentials, and publishing
   a rock through Dagger. The anonymous pull is already confirmed.

## 6. Already confirmed by spike

In `infra-defs/spike/` (git-ignored): the library renders a demo repo on Lua 5.4 and on
`gopher-lua` with byte-identical output in 0.06 s; eight invalid inputs are rejected with
file and line; a rockspec is read by the VM; a one-dependency Go binary builds in 6 s and
is 7.9 MB; an artifact is pulled from ghcr with the Go standard library alone.
LuaRocks 3.8.0 installs the spike rock, modules and `templates/` both; its lint asks only
for a license field.

## 7. Choices of mine inside this plan

Strike any that is wrong.

- `init` on a fresh repo pins the newest published `infra-lua` version.
- The rock version sits in `platform.toml` under a new `[rocks]` table.
- `infra-lua` publishes itself with `platform publish`, which needs one small new build
  framework for a repo with a rockspec: run the library's tests on the VM, then pack the
  rock as a one-layer image.
- `platform`'s own smoke spec, `tests.cue`, stays as it is: it is the smoke tool's input
  format, not part of render.
- The rockspec's license field reads `Proprietary`.
- `gh:prod9/infra-defs` is archived at the start. Repos on defs keep building from the
  modules already published to the registry; defs gets no further release.

## 8. Consequences to know

- **Installing platform** is unaffected. The launcher's `go install
  platform.prodigy9.co@VERSION` resolves through a tag served by the platform server
  already running at that name, and this plan does not touch that deployment.
- **Evaluation is eager.** A consumer cannot set an input of a def inside a finished
  pack, as `#components: deploy: #init_command` does in CUE. Packs take such inputs
  directly.
- **Output key order** is sorted with the Kubernetes head keys first, since Lua tables
  keep no order.

## 9. Not in this plan

- Moving `infra`, `infra-stage9` or any other repo to Lua; they get the guides.
- Taking the running platform server and its engine pool out of `prod9-main`.

### Slice 0: spikes

Spike code goes in `infra-defs/spike/` beside the existing ones (git-ignored); builds run
through a Dagu DAG modelled on `~/.config/dagu/dags/prod9-infra-rocks-spike.yaml`.

- **Validation.** A Go program using `github.com/google/jsonschema-go` that: loads
  Kubernetes' published OpenAPI v3 file for `apps/v1` and for core `v1`; loads the schema
  embedded in a Gateway API CRD; validates the documents in `spike/rocks/out51/`; and
  shows a deliberately misspelled field being rejected. Record build time and binary size
  with and without the library. It must answer: how much translation the OpenAPI 3.0
  dialect needs (`$ref` paths, `nullable`, `x-kubernetes-int-or-string`,
  `x-kubernetes-preserve-unknown-fields`); where the OpenAPI files are fetched from; and
  what `render` should do with a document whose kind has no schema available, which
  matters for a tenant repo that uses Gateway API kinds but does not render the CRDs.
- **Private ghcr.** Needs a scoped token: ask `ga42:prod9:control` for one limited to a
  test package under `ghcr.io/prod9` with read and write (rule `rule/policy-project`,
  "Resources" 5). Then: push the spike rock as a one-layer image through the Dagger SDK,
  the way `framework/platform_infra.go` builds the infra image; pull it with the
  standard-library puller in `spike/rocks/oci.go`, extended to send `REGISTRY_USERNAME`
  and `REGISTRY_PASSWORD` to the token endpoint.

### Slice 2: infra-lua library

- Port from `infra-defs/` at `v0.4.7`, translating each definition's inline `tests:`
  block into Lua tests; those blocks are the statement of expected output. Order: shared
  input fragments and probes (`attr/`); the pod controller and the workloads built on it
  (Deployment, StatefulSet, DaemonSet, Job, CronJob); core kinds (Service, Secret,
  ConfigMap, PVC, Namespace, ServiceAccount, the four RBAC kinds, PriorityClass, HPA,
  PDB, NetworkPolicy, Ingress); Gateway API kinds with the parent-reference rule; cert
  and policy kinds (ClusterIssuer, ClientSettingsPolicy); the three Flux kinds; the three
  Argo kinds; then the mixins (`parts/`: UseCertManager, UseKeel, PodResources,
  PodTolerations, NodeAffinity, PodSpread, PodMounts, AllowListenerSets); then the packs
  (Basics, WebApp, Postgres, Redis, Gateway, FluxTenant, Argo).
- Acceptance beyond unit tests: rewrite two or three apps from `infra-stage9/apps/` in
  Lua and compare the result with that repo's committed `k8s/` output, document by
  document, ignoring key order.
- Upstream helpers: finding documents by kind and name, and whatever editing help plain
  Lua does not already give. The download itself is a function `platform` provides.
  Check `platform/framework/skel/apps-nginx-gateway.platform` for archive extraction,
  which the DSL's `extract` verb covers today.
- Templates, converted from `platform/framework/skel/`: `apps-cert-manager.platform`,
  `apps-flux.platform`, `apps-nginx-gateway.platform`, `apps-cluster-issuer.cue.tmpl`,
  `apps-flux-sync.cue.tmpl`, `apps-gateway.cue.tmpl`, `defaults-basics.cue`,
  `defaults-webapp.cue`. Not converted: `apps-platform.cue.tmpl` (the server). Each
  template declares its vars and defaults first; today's defaults are in `infraVars` in
  `platform/framework/platform_infra.go`.
- The defs-to-Lua guide, built from the real conversions above.

### Slice 6: validation

Built from the validation spike's findings, inside `render`, before the tree is written.

### Slice 7: init and publishing

- `init` for an infra repo: resolve the newest `infra-lua` version from ghcr's tag list,
  fetch it, plan every file in the rock's `templates/` into `apps/` (and the defaults
  template to the repo root), collect each template's declared vars by running it in a
  declare-only mode, merge them into `[vars]` with the existing merge that keeps operator
  values, pin the version under `[rocks]`.
- A build framework for a repo with a rockspec: run its Lua tests on the VM, then build a
  one-layer image of the rock, so `platform publish` pushes it to ghcr.
