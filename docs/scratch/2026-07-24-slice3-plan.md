# Slice 3 — multiplex + observer/result redesign

Design is **locked** (chakrit, 2026-07-24). Next step: write it into `engine.md` /
`architecture.md` (spec-update slice) — precedes impl per the spec-leads Law.

## API — multiplex stays inside `engine/`

Multi-unit fan-out of already-resolved units is **parallel execution (engine's job,
capacity), not coordination** — so it stays in `engine/`, not an external `engine/multiplex/`
package. Consumers see only domain verbs, each taking an observer, returning a result:

```go
engine.Build(ctx, cfg, modnames, obs)        // []BuildResult
engine.Publish(ctx, builds...)               // []PublishResult
engine.BuildAndPublish(ctx, cfg, ..., obs)   // []PublishResult
```

- The generic `multiplexer[TIn,TOut]` (`engine/multiplexer.go`) stays **unexported**; it
  provides only orchestration/synchronizing and calls the same single-unit engine path
  internally (it never owns a build method).
- cmd and the srv worker call the **same verbs**, differing only in the observer they pass
  (CLI renderer vs `build_events` writer). Nobody outside `engine/` touches a multiplexer or
  a Run.
- The worker calls **one** verb per record; per-unit goroutines live inside the engine's
  multiplexer, never in the worker. The worker/scheduler boundary ("which build runs next",
  `engine.md:174-176`) stays out of `engine/`, untouched.
- preview reads the built container via the explicit method the spec already carves out
  (`engine.md:154-156`).

**This is essentially the current code** (`engine.go:172-202` already fans out via the hidden
multiplexer, returns `[]BuildResult`). The spec correction *deletes* the external
`engine/multiplex/` + "cmd drives the multiplex run" design (`architecture.md:113-114`,
`engine.md:198-207`); the worker boundary text stays.

## Observer — 5-method kernel

One method per `BuildEvent` kind. Two output events mirror the **build⊥publish orthogonality**
(delivery-verbs ADR); `ImageBuilt` is the common path — 4/5 cmd verbs are build-only
(`build`/`export`/`exec`/`preview` → `Build`; only `publish` → `BuildAndPublish`):

- `StepStarted(unit, step, at)` — lifecycle
- `StepDone(unit, step, at, err)` — lifecycle + step failure
- `ImageBuilt(unit, image, at)` — build's output (every successful build)
- `Published(unit, image, hash, at)` — publish's output (publish path only)
- `RunDone(unit, at, err)` — terminal status

Defer the log-capture callback (`engine.md:133-139`) until capture lands — add methods as
capabilities arrive, don't front-load.

## Observer composition + result-by-construction

- **`AccObserver`** — stateful fold; the engine **force-injects** one into every run, so it
  is the sole minter of the scalar result. (`Recorder` rejected — collides with test helper
  `run_test.go:61` and DB `record`/`BuildEvent`.)
- **`TeeObserver`** — FP fan-out: `Tee(obs ...Observer) Observer` forwards each callback to
  all children. Contract: **non-nil children only**.
- **Nil eliminated at the wrap site, once:**
  ```go
  obs := acc
  if caller != nil { obs = Tee(acc, caller) }   // Tee never sees nil
  ```
  So `report()`'s `if r.obs == nil` guard (`run.go:108`) is deleted, and `engine.md:109`'s
  "nil observer is a guarded skip" becomes "engine always injects an `AccObserver` → a run's
  observer is never nil; a nil caller just means no `Tee`".
- **`Run.Result()`** changes `(*dagger.Container, error)` → `BuildResult`, joining `acc`'s
  scalar fold (unit, ok/err, image, hash) with the Run-owned live `container` (`run.go:31`).
  That join is the **single by-construction site**; the `engine.go:200` hand-pack disappears.
  Illegal `BuildResult` states become unconstructable — the result is *derived* (folded from
  the stream) not *authored*.

## BuildResult / cache column — decision (a)

- The **live container** (`*dagger.Container` + `client`) cannot ride the scalar observer or
  cross to the DB — it stays **Run-owned**, engine-internal.
- The **scalar outcome** (unit, ok/err, image, hash) is the fold of the observer callbacks —
  identical in-process (cmd → in-mem `BuildResult`) and in-DB (worker → `build_events`).
- `BuildEvent` (`build_events` table) is the persisted stream; a materialized terminal column
  is legit only as a **derived projection** of that stream (rebuildable, never independently
  authored — the moment it's authored-not-derived, the stored `state` the spec killed is back).
- This is **slice 4** (`BuildEvent` fold + worker) — it does not change the slice-3 API. But
  the slice-3 spec correction must **not** parrot "everything is a fold" without noting the
  observer now carries output events (`ImageBuilt`/`Published`), nor "`BuildResult` discarded"
  (`platform-server.md:194-197`) — the engine struct's *scalars* survive as the fold; only its
  live-container form dies on the srv side.

## The rulings behind it — chakrit, verbatim

Frozen here when the ledger item was trimmed on graduation (2026-07-26, `0c50837`). The
design of record is the spec; these are the words it was built from.

- **Multiplex stays inside `engine/`, exposed via domain verbs** — "hide the mujltiplexer
  inside engine/ as in expose multiplexer access through engine/ methods rather than letting
  outside package access multiplex/ directly".
- **The multiplexer is pure orchestration, owns no build method** — "The multiplexer should
  not concern themselves with individual builds, it should just provide the
  multiplexing/orchestration/synchronizing and use the same build methods as engine
  internally".
- **`BuildResult` survives and must be consistent by construction** — "We'd still need proper
  result type"; "make it so that even the tee collector doesn't have to deal with nil".
- **Two output events** — "Don't we need something like ImageBuilt also?"
- **Names** — "Accumulator is cool and we can perhaps shorten it to Acc like
  AccObserver+TeeObserver". (`Recorder` rejected: collides with the test helper at
  `run_test.go:61` and the DB `record`/`BuildEvent` vocabulary.)
