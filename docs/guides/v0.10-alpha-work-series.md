## 1. Apply stored publication policy

Current worker execution chooses publication from `refs/tags/` alone in
`srv/builds/build_module_job.go`. Policy is already resolved and persisted through
`conf.Model.ResolvePublishPolicy`, manifest parsing/recording, and the immutable manifest
snapshot bound to each admitted build; the worker request currently omits that policy.

First reconcile the Phase 3 deferrals in the execution-mode and server specs, preserving
the settled policy matrix:

| Stored policy | Branch build      | Tag build             |
|---------------|-------------------|-----------------------|
| always        | Publish as latest | Publish as latest     |
| tags          | Build only        | Publish exact git tag |
| never         | Build only        | Build only            |

The server build domain owns one publication selection from persisted policy and
recorded ref. Use that selection for both credentials and the engine verb. Read the
build's immutable snapshot, not a later branch manifest or an inferred policy. Reuse
existing engine verbs and registry-token handling; leave local CLI behavior intact.
Reject corrupt stored policy before credentials or engine execution.

Acceptance: cover the entire matrix, exact tag preservation, build-only execution without
publication credentials, and an admitted build remaining independent of later manifest
observations. After rollout, verify controlled branch/tag builds, their recorded publish
outcomes, and actual registry tags. Registry publication alone does not prove rollout.

Release checkpoint: first new alpha with live publication-policy evidence.

## 2. Complete repository history

`RepositoryBuilds.svelte` requests and retains three builds. The existing repository
build API returns newest-first results with a default/cap of 50 and no cursor. Implement
a clearly bounded latest-50 history feed. Arbitrary older browsing would require a
separate pagination contract and is outside this increment.

Update the first-build scope in the web UI spec before implementation. Keep the landing
page's three-build preview, whole-repository Start build form, explicit Refresh, and
actual detail links. Present canonical status, exact ref/full SHA, source timestamps,
module outcomes, and truthful trigger provenance. Define actor presentation from
available authorized fields rather than inventing names from numeric user IDs.

Adapt the landing's compact rows, outcome marks, facts, and time helpers before
extracting shared feed presentation for these two concrete consumers. Preserve v2027
component ownership. The bounded history itself needs no API or database change.

Acceptance: more than three real builds visible newest-first, accurate links and module
outcomes, distinct loading/empty/refused/offline states, and failed Refresh retaining an
explicitly stale snapshot. Long values must remain usable at narrow widths; submission
must remain single-request with accepted-build feedback.

Release checkpoint: live history and refresh against real recorded builds.

## 3. Review a ref and queue selected modules

Use a read-contract sub-slice followed by the wizard/admission sub-slice, with a separate
spec commit before each implementation change. Release the complete reviewed-build
capability rather than an isolated preview endpoint.

Reuse GitHub ref resolution, immutable-commit manifest reads, manifest parsing, and
transactional selected-module admission. Extend the existing manifest resource through
its REST surface; settle the query/response contract in the server spec first. Preview
reads source and never creates a build.

Design gate: queueing currently accepts a ref and resolves it again; SHA is server-owned.
Choose pinned reviewed source or refusal/re-review if the ref moved. Recommended for
discussion: refuse a moved ref and require review again, preserving ref resolution at
admission. Never display modules for one commit while silently queueing another.

Wire the real `/repos/{owner}/{repo}/builds/new/` route, including the server HTML
classifier. Replace canned data with ref entry, resolved SHA, manifest/module review,
all modules initially selected, and explicit confirmation. Ref edits invalidate review.
Define how the existing simple Start build form coexists with or links to the wizard.

Acceptance: distinguish missing ref, inaccessible repo, missing/invalid manifest, and
transport failure; preserve authorization. Verify the moved-ref ruling, reject empty
explicit selection, admit only selected modules, suppress duplicate submission, and open
the accepted build's actual detail. Live checks use multiple modules and a controlled
moving ref, including session expiry, loading/disabled states, and narrow layouts.

Release checkpoint: selected real modules execute at the source promised by review.

## 4. Add linked operator retry

The API already accepts `retry_of`, validates a same-repository predecessor, and sets
the retry trigger. The current server spec re-resolves the same repository/ref and reads
a new manifest; retry does not mean replaying the predecessor's SHA.

Design gate: settle which builds expose retry, whether original module selection is
carried or reviewed afresh, and how missing modules at the new head are handled.
Preserve ref re-resolution unless chakrit changes that contract. Update server and UI
specs before implementation.

Reuse build creation, selection admission, and recorded detail. Add an explicit action
and predecessor navigation. Preserve earlier attempts and the existing single build
model; do not automatically resubmit after a network error.

Acceptance: one action creates one new linked build, preserves the original, records
retry ancestry/trigger, and follows the approved ref/module behavior. Refusals and failed
admission stay visible. Live proof follows a real failed build with a successful linked
attempt and inspects both histories and captured output.

Release checkpoint: deliberate recovery with traceable new attempts.

## 5. Replace the mock engine fleet

The target UI requires reachability, version, and authorized current work, while the
engine spec keeps resolver/dial mechanics private. Reconcile this boundary first: design
a proper read-only engine inspection operation owning discovery/probing, rather than
exporting private helpers or duplicating DNS logic in `srv`.

Use existing roster configuration. An inspection of an unconfigured/empty fleet must
not provision the SDK's local engine. Distinguish empty roster, lookup failure,
unreachable instance, and version-read failure. Verify the sanctioned version query
before including it; do not fabricate uptime/cache totals.

After engine/server/UI spec changes, add a self-contained server engines fragment and
real fleet presentation. Reuse normalized module assignments, filtered by GitHub access.
Before liveness reconciliation exists, an assignment without `run_done` proves recorded
unfinished work, not active execution. Label that distinction and its observation time;
do not infer actual engine activity or idleness from these records. Integrate the ruled
liveness representation when increment 7 lands. The server consumes inspection, not
execution scheduling.

Acceptance: real data and Refresh; honest empty/error/partial states; work links only
to readable repositories/builds; no unauthorized metadata. Test through sanctioned
interfaces, never manual engine commands. Verify in Chrome while controlled work runs.

Release checkpoint: a truthful fleet overview useful independently of instance pages.

## 7. Reconcile stalled work without inventing completion

Research this dependency during earlier increments; implement after the design gate.
The recorded ruling is a reconciliation loop with human retry, not automatic requeue.
Its window, observation mechanism, and wire/status representation are unsettled.

Output is buffered until step completion, so an old observation can mean a healthy
quiet step. A claim is not proof of continued worker liveness, and missing `run_done`
is not proof of death. Distinguish no recent observations from authoritative abandonment.

Design gate: agree the evidence for quiet versus abandoned work, its window, late-arrival
behavior, and whether the result is derived or durably recorded. Verify the pinned fx
worker's public surface directly; its historical reference is insufficient. If reliable
death detection or cleanup capacity requires an absent fx affordance, obtain a ruling
for a proper upstream feature before platform builds on it. No private queue reads,
shadow worker machinery, or arbitrary timing increases.

Then update server/engine/UI specs separately from implementation. Reuse result folds
and domain job scheduling where they satisfy the ruled contract. Preserve append-only
history, idempotence and concurrency safety; do not invent engine completion, clear
claims for redispatch, or rewrite completed outcomes.

Acceptance: unclaimed, recent, quiet-but-active, interrupted-before-first-event,
completed, and late-resuming work follow the ruling. Verify unchanged terminal results,
safe repeated reconciliation, and human retry producing a new build. Live proof uses
disposable work and supported failures, not killed shared workers or edited DB rows.

Release checkpoint: stale work explained truthfully with deliberate recovery.

## Repeating completion and delivery gates

1. Re-orient from current specs/state/authority and resolve the increment's design gate.
   Keep unrelated `.gitignore` changes outside scoped commits.
2. Commit specs first. Search existing owners/components before adding units.
3. Implement with structural prevention and meaningful behavior tests, preserving fx's
   public composition surface and shared-package dependency direction.
4. Run targeted checks, frontend tests/static build for UI changes, `go test ./...`, and
   `./test.sh`. Review smoke drift before recording it. Preserve budgets and use
   `nice -n 19` for approved resource-intensive runs.
5. Audit the whole increment, fix in-scope findings, verify again, and commit coherently.
   Include regenerated embedded UI when source changes require it.
6. Follow [cutting a release](cutting-a-release.md) with the next unused alpha: publish
   the image, push the branch/tag, create a GitHub prerelease, and retain post-tag smoke.
7. Hand the exact published image tag, expected behavior, checks, and schema/SDK
   compatibility notes to infra. It follows its repository's rollout instructions.
   Platform's kubectl use remains read-only. Any schema change needs a new forward
   migration and an explicit compatibility/recovery plan.
8. Confirm Flux/rollout health, server/worker readiness, logs/events, and HTTPS. Accumulate
   the increment's functional and desktop/narrow layout checks for final Chrome/user
   acceptance after the series, rather than blocking each increment on browser access.
9. Record commit/tag, image, infra evidence, browser results, and unresolved findings;
   close only verified scope and advance to the next increment.
