How GitOps works in platform

platform delivers software by making the git repository the single source of truth: every desired-state fact — including the container image ref — lives committed in CUE, and Flux reconciles it onto the cluster. Two phases: bootstrap the appliance once, then run the steady-state deploy loop forever.

Flux only ArgoCD — deprecated Keel — deprecated

The one rule: render is a pure function of the committed git tree (apps/*.cue + platform.toml). Nothing that decides what runs — least of all the image ref — is injected at render time. To change what's deployed, you change git. Flux is the sole GitOps engine; ArgoCD and Keel are gone.

Phase 1 — Bootstrap the appliance

platform is an opinionated appliance: it ships the cluster setup, not a toolbox. Onboarding a fresh infra repo writes the baseline sources into git…

infra-repo/ platform.toml # [vars] — version pins and ingress hosts cue.mod/ # pins prodigy9.co/defs apps/ # *.cue apps + *.platform directives defaults/ # shared CUE definitions

Initialization writes the baseline into the infra repo; the operator commits its values, renders it, and bootstraps the cluster with server-side kubectl apply. The baseline owner installs these shared components:

What lands on the cluster

  • cert-manager — issues TLS.
  • Flux — the in-cluster GitOps reconciler. From here on Flux is what applies desired state; nothing is kubectl apply-ed by hand.
  • NGINX Gateway Fabric — Gateway-API ingress.
  • Gateway and ACME issuer — shared ingress and TLS configuration.
  • Platform server seed — review runtime configuration and a separate worker before running the API, installation wizard, and web UI.
  • Dagger engines — a privileged StatefulSet, the in-cluster build substrate. platform finds the pods through the headless Service's DNS A-records and picks one uniformly at random for each engine connection.

Cold-start has no unbreakable cycle: the engine ships as plain manifests platform renders for operator bootstrap, and the first platform image is built by an SDK-managed local engine. Later workers can use the in-cluster engines. A tenant joining this cluster emits only its own Flux source and Kustomization; it does not install another baseline.

Phase 2 — The deploy loop

Once the appliance is up, every deploy is the same loop. The git commit is the gate; everything downstream is mechanical and reproducible from it.

  1. App publish — a publish operation builds and pushes the app image. The local CLI invokes it explicitly; the server applies its separate delivery policy. build alone pushes no image, and release only cuts a tag.
  2. commit the ref — that immutable ref is written into the infra repo's apps/*.cue as a committed literal, and committed. This commit is the deploy.
  3. platform render — evaluates the apps CUE package and applies the .platform directives into a manifest tree. A pure function of the committed tree: the image is read from the literal in CUE, never injected.
  4. Infra publish — the infra framework packs the whole manifest tree into one layer of a plain scratch image and pushes it under latest. Local operators use platform publish; the server's intended policy publishes successful infra builds. Environment separation belongs to the infra repo's CUE.
  5. Flux reconcile — an OCIRepository watches that tag, pulls the image, extracts its manifest layer, and applies it. The cluster converges to what git holds. One org-wide GitHub→Flux Receiver webhook accelerates the pull loop.

The loop closes on git: the next change is another commit, and Flux continuously drives the cluster back to the committed state.

Why the image ref lives in git

The image is desired state. If it entered at render time from a flag or env, the git source couldn't tell you what's deployed and a deploy couldn't be reproduced from the tree alone — the very thing GitOps exists to remove.

So the ref is a concrete value in apps/*.cue: deploying is a git commit, the rendered manifests derive from the committed tree, and Flux reconciles them.

Operator settings: [vars]

Versions and similar knobs the operator owns live in platform.toml under [vars] — also committed, so they too are desired state. They reach the baseline hooks by a single convention:

# platform.toml — env-style keys, the preferred form [vars] NGINX_GATEWAY_VERSION = "v2.6.7" # consumed lowercase-derived by both render routes: # CUE apps/*.cue → #version: string @tag(nginx_gateway_version) # DSL *.platform → download "…/\(nginx_gateway_version)/…"

Same git rule: var values come only from committed platform.toml, never an environment variable at render time. platform attaches no meaning to any var — it is a pure name→value passthrough.
